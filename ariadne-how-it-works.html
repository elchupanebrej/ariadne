1. Methodology: systematic inventive thinking

Nine formal operations on the state of an engineering problem — the foundation Ariadne is built on

    O8 --> O9["9. Validate
verify + transition"]
    O5 -.->|"evidence request / result"| O9
Ariadne is not a set of prompts — it is a software adaptation of systematic inventive thinking (SIT, the modern branch of TRIZ) for engineering tasks. The methodology claims that any engineering problem can be decomposed into nine operations: formal transformations of the problem state. Each operation has a strict definition — its input, the action it performs, and its expected output. The operations follow the natural path of reasoning: first understand and model the problem (Frame), then find the cause or contradiction (Diagnose), propose changes to the system (Transform), explore the space of alternatives (Explore), fill the gaps in knowledge (Knowledge), account for dependencies and boundaries (Dependencies), check behavior over time and under load (Dynamics), select a candidate by value (Value), and finally confirm the solution by execution and transition safely (Validate). Every branch of reasoning ends in one epistemic chain: observed failure → diagnosis → model → hypothesis → transformation → executable check → empirical evidence → justified decision.

2. Formal problem model

Problem state S_t is a tuple of requirements, invariants, contradictions, candidate mechanisms, and the epistemic graph

flowchart TD
    ST["Problem state S_t"] --> B["B_t — behavioral requirements"]
    ST --> I["I_t — invariants"]
    ST --> C["C_t — contradictions"]
    ST --> M["M_t — candidate mechanisms"]
    ST --> E["E_t — epistemic graph"]
    C --> SP["separation: in time /
in data / in modes / across boundaries"]
    E --> PR["provenance: U ⊏ A ⊏ P ⊏ D ⊏ M ⊏ F ⊏ L"]
    E --> LAD["evidence ladder — 10 rungs"]
The methodology introduces one formal representation of any task — the tuple S_t. Behavioral requirements (B_t) describe what the system must do; invariants (I_t) are properties that must never be violated under any circumstances; contradictions (C_t) are the places where requirements conflict with each other; candidate mechanisms (M_t) are structurally distinct solution variants; the epistemic graph (E_t) is the map of where every claim came from. Two kinds of contradictions are distinguished: technical (improving one parameter inevitably degrades another) and physical (one component must simultaneously possess mutually exclusive properties). Following TRIZ, contradictions are not "balanced" by compromise — they are eliminated with separation principles: in time, in data ownership, in operating modes, or across system boundaries. The epistemic graph is an overlay of typed metadata around the work plan: it records where each claim originated and how reliable it is, but it does not replace a task tracker.

3. Overview: from task to decision

The full path: the agent receives a task, applies rules, writes to the graph, passes gates, and emits a report

    D --> E["Graph mutations

    E --> F["Gates
structural → semantic → epistemic"]
    F -->|"passed"| G["Report: decision tree

    F -->|"diagnostics"| D
    G --> H["DEC — locked decision"]
    S["Subagents
(adversarial, spike)"] -.->|"envelope ariadne-delta"| E
Work starts when the agent (an LLM) receives a task or a description of a symptom. Its first step is to consult the ariadne skill — a dispatcher file that decides which branch of the methodology fits the situation and directs the agent to a specific rule file (rules). The rules say which operations to perform and which nodes to create; the agent executes them through the ariadne command-line utility. Each command adds or changes nodes and edges in the epistemic graph — the persistent store of the entire reasoning process. Before a decision can be locked, the graph passes a series of automated checks — the gates; if a check reports problems, the agent returns to the operations and refines the model. When all checks pass, a report is generated — a decision tree with a change log that shows how and why the result was reached. Along the way, subagents (e.g. an independent critic or a hypothesis investigator) may contribute; they can only touch the graph through schema-validated envelope packages.

4. The epistemic graph

Ariadne's core store: typed claim nodes, dependency edges, and a provenance mark on every claim

    C1 --> R["EVDREQ

    R --> V["EVD

    V --> D["DEC

    subgraph Provenance
        direction LR
        U["UNKNOWN"] --> A["ASSUMED"] --> P["PROPOSED"] --> DER["DERIVED"] --> M["MEASURED"] --> F2["FACT"] --> L["DECIDED"]
    end
All of Ariadne's work happens on the epistemic graph — a directed graph where each node is one claim with a role: FRAME is the problem statement, HYP is a hypothesis about the cause, CAN is a candidate mechanism, EVDREQ is a request for verification, EVD is the verification result, DEC is the accepted decision. Edges express dependencies between claims (e.g. "this hypothesis explains the symptom" or "this decision relies on that candidate"). The most important attribute of a node is its provenance — where the claim came from and how trustworthy it is. Provenance forms a ladder of rigor, from UNKNOWN through ASSUMED (assumption), PROPOSED (proposed), DERIVED (derived), MEASURED (measured), and FACT up to DECIDED (locked by decision). The weakest-precondition rule applies: a derived claim can never be more reliable than its weakest premise. Hypotheses must carry falsification conditions — criteria under which they count as disproven — and verification results must carry a verdict (supported / falsified / inconclusive).

5. Storage: an event log

The graph is not stored as a ready file — it is rebuilt by replaying an append-only journal of events

flowchart TD
    A["ariadne node add / edge add"] --> B["Process queue +
mkdir lock
(stale 5 min)"]
    B --> C["append: GRAPH.jsonl
node | edge | tombstone"]
    B --> D["STATE.yaml
frontier, open_unknowns"]
    C --> E["Replay all events
→ materialized graph"]
    E --> F["Integrity check
+ gates"]
    E --> G["INDEX.md
node cards"]
Physically, Ariadne stores the graph in the .ariadne/ directory as a journal of events — the GRAPH.jsonl file, to which every command appends one line: node creation, edge creation, or edge removal. Edge removal is recorded as a special tombstone event, so the history of reasoning is never erased — it can be replayed from the start to obtain the graph in any state. This design guarantees reproducibility: two agents reading the same journal always see the same graph. Parallel processes are protected by an in-process queue plus a filesystem lock (a lock-directory with protection against stale holders). Separately, STATE.yaml keeps service state: the list of unfinished nodes (frontier) and open questions (open_unknowns), which tells the agent what is still pending. An INDEX.md with human-readable cards for all nodes is generated alongside.

6. Operations and rule routing

The agent does not improvise: every task branch routes to exactly one rule, which dictates the operation

flowchart TD
    A["Task branch"] --> B{"What is it?"}
    B -->|"requirements"| R1["10-frame"]
    B -->|"symptom → cause"| R2["20-diagnose"]
    B -->|"transform"| R3["30-transform"]
    B -->|"structural candidates"| R4["40-explore"]
    B -->|"unknown facts"| R5["50-knowledge"]
    B -->|"links / boundaries"| R6["60-dependencies"]
    B -->|"queues / dynamics"| R7["70-dynamics"]
    B -->|"candidate selection"| R8["80-value"]
    B -->|"verify / transition"| R9["90-validate"]
    R1 & R2 & R3 & R4 & R5 & R6 & R7 & R8 & R9 --> O["ariadne op <operation>"]
    O --> M["graph mutation"]
The key idea of Ariadne is that the agent must not decide "by feel" which technique to apply. The dispatcher (SKILL.md) analyzes what exactly arrived: requirements without mechanisms, a symptom without a cause, a need to transform something, several solution variants, a shortage of facts, questions about coupling between modules, behavior problems under load, selection among candidates, or the need for verification and a safe transition. Depending on the answer, the agent loads exactly one rule file — for example rules/20-diagnose.md for causal analysis or rules/80-value.md for candidate selection. The rule is an instruction that specifies which nodes, edges, and checks must be created, and it invokes the corresponding CLI operation (ariadne op diagnose, etc.). The console command is a thin wrapper: it only prints which rule was activated; all substantive work happens in the graph according to the rule.

7. Gates: structural → semantic → epistemic

Automated checks that prevent locking a decision without evidence of the required rigor

flowchart TD
    G["Graph"] --> S["Structural
graph integrity, valid edges"]
    S --> SE["Semantic
semantic consistency"]
    SE --> E["Epistemic"]
    E --> C1["claim-class →
minimum ladder rung"]
    C1 --> C2["EVDREQ confirmed by EVD
with sufficient rung"]
    C2 --> C3["TRANS: lifecycle,
deadline, verification"]
    C3 --> C4["adversarial critique present"]
    C4 --> P{"All passed?"}
    P -->|"yes"| OK["verify: ok"]
    P -->|"no"| DIAG["diagnostics with codes
→ back to operations"]
Gates are deterministic (model-independent) checks of the graph, run with ariadne verify. The first, structural gate, checks integrity: do all nodes referenced by edges exist, are the link types valid. The second, semantic gate, checks that claims are meaningfully consistent. The third, epistemic gate, is the strictest: it matches the class of every claim against the minimum admissible rung of the evidence ladder. For example, a claim about syntactic structure only requires rung 2, while a claim about the safety of a distributed system requires rung 8 — "plausible" is not counted there. Every evidence request (EVDREQ) must have a corresponding result (EVD) with a sufficient rung. Transitions (TRANS) are checked for lifecycle state, deadline, and verification confirmation, and key decisions for the presence of adversarial critique. If a gate fails, it returns a list of diagnostics with codes, so the agent knows exactly what to fix.

8. Transitive invalidation

New evidence disproved a hypothesis — statuses cascade across all dependent nodes

graph TD
    EVD["EVD
verdict: FALSIFIED"] -->|"falsifies"| HYP["HYP
FALSIFIED"]
    HYP -->|"invalidate"| CAN["CAN
INVALIDATED"]
    HYP -->|"invalidate"| CLM["CLM
NEEDS_REVIEW"]
    CAN -->|"invalidate"| DEC["DEC
RE-OPENED"]
    CAN -->|"invalidate"| TRANS["TRANS
BLOCKED"]
    TRANS -->|"mandatory"| DC["Decommissioning Contract
retirement predicate + cleanup test"]
Reasoning is not static: new empirical data can arrive at any time and disprove previously accepted hypotheses. The operation ariadne invalidate HYP-x --by EVD-y handles this case: it first verifies that the evidence EVD actually falsifies the given hypothesis, then runs transitive invalidation — updating statuses along the chain of dependencies. The hypothesis is marked FALSIFIED; candidate mechanisms that relied on it become INVALIDATED; related claims are flagged NEEDS_REVIEW; accepted decisions are RE-OPENED; and planned transitions are BLOCKED. Nothing is physically deleted: the old events stay in the journal, and the whole path of reasoning can be traced. This lets the system "fail honestly": instead of burying disproven assumptions, it marks them explicitly and forces a re-examination of everything built on top of them.

9. Reports, subagents, and host integration

How results leave the graph (reports) and how outside contributions enter it (envelopes, adapters)

    A->>C: ariadne report FRAME-x

on assumption falsification
The final stage turns the graph into artifacts that humans and other systems can read. The ariadne report command traverses the decision tree from the original problem statement down to locked decisions and produces a text report with a change log — from which one can reconstruct why every decision was made. The ariadne viz command builds a self-contained HTML projection of the same tree for visual review. The second flow is input: subagents (an independent critic, a hypothesis investigator) have no direct access to the graph; they submit their proposals as ariadne-delta envelopes — structured JSON packages that the CLI validates against a schema and applies to the graph. The third flow is integration with host systems: the GSD adapter receives operational notices (NOT-*) when assumptions are falsified, so an external planner is aware of the risks; the Matt adapter imports data from other tools; and the orchestration layer (harness) allows a session to continue in a fresh environment. The depth of processing is controlled by the Fast / Standard / Deep mode — the deeper the mode, the more mandatory checks.
